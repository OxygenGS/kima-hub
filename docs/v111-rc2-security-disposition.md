Also installed: Debian `ffmpeg` version `7:5.1.9-0+deb12u1`. The backend streaming implementation `backend/src/services/audioStreaming.ts` uses a **separately bundled** `@ffmpeg-installer/ffmpeg` binary to transcode to MP3 with `libmp3lame`. The Python `services/audio-analyzer/analyzer.py` uses Debian `ffprobe` and `ffmpeg` to decode the **first audio stream** to PCM with explicit `-vn -sn -dn`. No AV1 *encoding* call is present in those inspected paths, lowering direct exposure to the libaom AV1-encoding-specific CVE, but does **not** rule out other codec, parser, protocol, transitive or unreviewed call paths. No binary library has been removed.

Debian's description of [CVE-2026-34873](https://security-tracker.debian.org/tracker/CVE-2026-34873) specifies Mbed TLS **3.5.0 through 4.0.0**, while this binary is **2.28.3-1**. Debian's own Bookworm package tracker nevertheless labels the source vulnerable. Upstream Mbed TLS explicitly lists only 3.5.0–3.6.5 and 4.0.0 as affected (see [official advisory](https://mbed-tls.readthedocs.io/en/latest/security-advisories/mbedtls-security-advisory-2026-03-client-impersonation-while-resuming-tls13-session/)), providing strong **potential non-applicability** evidence for our 2.28.3 binary; the conflicting Debian/Trivy source-package classifications remain visible for explicit review. Separately, [Mbed TLS's own CVE-2026-34875 advisory](https://mbed-tls.readthedocs.io/en/latest/security-advisories/mbedtls-security-advisory-2026-03-ffdh-buffer-overflow/) limits its affected versions to 3.5.0–3.6.5 and TF-PSA-Crypto 1.0.0, also excluding the installed 2.28.3 branch in its own advisory. Neither is marked accepted/cleared until the maintainer reconciles source-package mapping and exact compiled-library use. Debian also explicitly marks [CVE-2023-45853](https://security-tracker.debian.org/tracker/CVE-2023-45853) as **ignored** for its Bookworm zlib build because the affected MiniZip contribution was not compiled into the distribution package. This justifies investigating a targeted scanner disposition, not a blanket allowlist for zlib or separately bundled MiniZip copies.

For the three Mbed TLS findings, Debian [`librist4`](https://packages.debian.org/bookworm/librist4) depends on `libmbedcrypto7`, and [`libavformat59`](https://packages.debian.org/bookworm/libs/libavformat59) depends on `librist4`. Purging a suspect library in isolation will break legitimate FFmpeg package dependencies. No cross-release `apt` mixing or package removal without a full runtime compatibility test.

## Additional shipped FFmpeg binary — independent hardening experiment (NOT in rc2)

Source inspection of the **exact rc2 application runtime** found that backend `src/services/audioStreaming.ts` imports `@ffmpeg-installer/ffmpeg` and configures `fluent-ffmpeg` to use its bundled binary for MP3 transcode. The release backend lockfile has `@ffmpeg-installer/linux-x64` version `4.1.0` and `@ffmpeg-installer/linux-arm64` version `4.1.4` as optional architecture packages, **in addition** to distro-managed Debian FFmpeg `7:5.1.9-0+deb12u1`. Python audio analysis independently invokes the Debian `ffmpeg` and `ffprobe` commands. A Debian package-level Trivy scan cannot by itself prove the security posture of this bundled standalone executable, and no CVE exploitability is claimed.

A **separate no-publish experimental branch** `feature/v111-ffmpeg-runtime-hardening` replaces the backend's extra FFmpeg binary dependency with the system FFmpeg, retaining `fluent-ffmpeg` and `libmp3lame` usage. The independent [experiment #39103047880](https://github.com/OxygenGS/kima-hub/actions/runs/39103047880) finished successfully: npm lockfile consistency, distribution FFmpeg MP3 encoding/ffprobe, Prisma database migration, TypeScript compilation, and targeted audio-streaming/waveform Jest regression all passed. A second [native Debian Bookworm compatibility run #39103241775](https://github.com/OxygenGS/kima-hub/actions/runs/39103241775) passed **all 3 jobs** on experimental source `a3471a8f99f7c1ea91e89f7bce7c9be9b48f3886`: actual Debian 12 FFmpeg MP3 encoding, ffprobe and waveform PCM decoding succeeded separately on native AMD64 and ARM64, while backend package install/Prisma/TypeScript and **53 targeted Jest tests** also passed on disposable PostgreSQL/Redis. The no-publish experiment is based on PR #7 but includes backend-only changes on `feature/v111-ffmpeg-runtime-hardening`. It has **not** been compiled into a full multiarchitecture AIO image, run through complete v1.11 E2E or published. **No experimental application changes are part of PR #7 or the published rc2 image.** Even after passing lightweight CI, a change like this requires new native AMD64/ARM64 assembled-image tests, real audio seek/transcoding and independent migration/rollback; a newly published candidate would need separate authorization before treating this as release source.

## Privilege and secret boundaries — confirmed source, incomplete runtime mitigation

- Dockerfile supervisor runs as **root**; its `postgres` and `redis` programs explicitly drop privileges, and frontend explicitly uses `kimaweb`. Real published-image smoke logged a non-root `kimaweb` frontend process.
- The **backend**, `audio-analyzer` and `audio-analyzer-clap` program entries contain **no `user=` directive**, therefore inherit supervisor's root identity. Non-root backend/analyzer hardening remains **open**. Do not suggest the successful frontend check covers all processes. The actual *published rc2* audit independently confirmed this same user mapping on **both** architectures (PostgreSQL=`postgres`, Redis=`redis`, frontend=`kimaweb`; backend and both analyzers=root).
- Fresh AIO PostgreSQL and backend bind to loopback; PostgreSQL HBA rejects remote addresses, including on restored old datasets. Published-image disposable smoke verifies loopback boundaries and denies unauthenticated writes. Those findings do not mean an attacker already running inside the same container is unprivileged.
- The persistent PostgreSQL credential is randomly generated under `/data/secrets/database_password` with mode 0600, and `/app/backend/.env` is also mode 0600. Backend is root today; before dropping to a dedicated UID, refactor local database readiness checks and carefully establish **minimum** read/write permissions to app state and needed secret material without exposing secrets to the frontend or music-directory peers.
- Privilege changes should be developed and validated separately; they change the running artifact and would invalidate rc2 as an exact-source candidate. Rebuild/publish a **new** candidate only after the security change passes native AMD64/ARM64, real auth/audio, old-image upgrades and independent rollback.
- No evidence here demonstrates an actual successful exploit, and no release-owner acceptance has been recorded.
